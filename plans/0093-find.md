# 0093 — Find: the first row is the file you meant, and search is as fast as `rg`

- Status: **in force** for the find release (0091 §7 "0.58 — find", renumbered 0.60)
- Date: 2026-11-10
- Adopts 0091 §4.1, §4.2, §4.6 (B8), §5.4 (B1, B8, B12). Answers to 0088 (the look).

## 1. Why

0091 measured the finder and project search on the Linux tree (97K files) and
found them fast and wrong: Enter opened the second row (B1), `sched.h` listed
twelve exact names in alphabetical directory order, nothing remembered what the
user opens, every search re-walked the tree on one thread (1.15–1.3 s where `rg`
takes 0.1–0.2 s), the three toggles every editor has were typed qualifiers, and
a references list was rows of identical clipped absolute paths (B8).

## 3. The finder

### 3.1 The bar rests on the top row (B1)

`Picker::install_ranking` carried the selected *item* across every re-rank, so
the first batch's top row was followed down the list as better matches
streamed in. Rule: **until the user moves the bar for the current query, every
installed ranking leaves it on the resting row** — row 0. A bar the user moved
follows its item, as before. A query change is a new question and resets it.

Enter is unchanged and already right: while a ranking is in flight it waits
for that ranking, then opens its top row. Enter never waits for the walk to
finish — it opens the row under the bar, which is the best match of what has
loaded (fzf and Telescope do the same; on a cold 100K-file tree the
alternative is a dead Enter key for seconds).

### 3.2 A file name outranks a directory

Each term is tried against the file name first. A name match scores
`NAME + nucleo score + coverage`, where coverage is the share of the name the
term spells (VS Code's prefix bonus); a term that spells the *whole* name adds
`WHOLE_NAME`. Only a term the name rejects, or one containing `/`, is matched
against the whole path, and earns no bonus. `NAME` exceeds any score a path
can earn, so no directory match outranks a name match. Ties go to the shorter
path, then tree order.

### 3.3 Terms

Whitespace separates terms; every term must match; a row's score is the sum.
No `!`, `^`, `$`, `'` operators — the qualifier language (`-path:`, `glob:`)
already excludes and anchors, and two operator syntaxes in one field is one
too many.

### 3.4 Frecency and the empty query

`RecentFiles` (engine, `picker/recent.rs`): per project, per file, a visit
count and the project clock at the last visit. The clock ticks once per file
visit, not per second: score = visits × weight(age in visits), weights
8/4/2/1 at ages <8/<32/<128/older. **Logical time is deliberate** — the order
is a pure function of what was opened, so replay reproduces it, tests need no
clock, and a project left for a month comes back in the order it was left.
512 entries per project; the weakest is forgotten.

It is persisted with the session: same state directory, same project key,
same private atomic publication, written by the same worker on every session
capture, in its own file (`strop/recent/<key>.json`) because a session is
replaced by each capture while this record accumulates, and reading it at
startup must not parse undo history. Names and counts only. It is part of the
replay seed.

The finder's *priors* are, best first: the other open files most recently
used first, the current file, then frecent files. On an **empty query** they
lead the list in that order, then the tree. On a **typed query** a prior adds
a bonus of 48/32/16 points by place (about three matched characters at most):
among equal matches the familiar file leads; a better match still wins.

*Deviation from 0091's wording.* 0091 asks for "those three, most recent
first". The current file is listed after the other open files instead, so
`Space f` Enter is the file you were just in rather than a no-op — the same
complaint 0091 makes about `Space b`, and what VS Code's quick open does.

### 3.5 Keys in the field

- `Ctrl-U` deletes from the caret back to the start (readline; B12).
- `Alt-H` / `Alt-I` flip hidden and ignored files (fzf-lua's chords).

### 3.6 Buffers

`Space b` lists most-recent-first with the current buffer leading; the bar
rests on row 2, the alternate. Typing returns the bar to the best match.

### 3.7 Search toggles and case

`Alt-C` match case, `Alt-W` whole word, `Alt-R` regex (VS Code's chords), in
both the Find and With fields. They are `SearchModes`, session state that sits
**in front of** the query language: `SearchQuery::parse_with(text, modes)`
re-reads the parsed expression — bare text becomes a pattern, the expression is
wrapped in `\b(?:…)\b`, an absent `case:` becomes sensitive. The typed text is
never rewritten, and an explicit qualifier wins over a toggle. `Space R`
shares the field and therefore the toggles; nothing else about replace changes.

The toggles are the session's, not one picker's (VS Code's are too): a
reopened search keeps them. That is safe only because they are always
visible: the **status row** under the field names, in words, everything that
differs from the default — `match case · whole word · hidden files skipped` —
and is absent when nothing does (0088 rule 4). The engine words it from the
same state the source request reads; the renderer prints it. It replaces the
old `namespace · mode · hidden on (session) · …` summary, which compared the
session against itself and so never reported a session toggle.

`:search-options` is deleted: it flipped the configuration in place, which is
why the row above could not see it. One mechanism, two keys.

**Case is smart everywhere a query is typed**: finder, project search, `path:`
scopes and buffer `/` `?`. All-lowercase matches either case; one capital
makes case count (ripgrep `--smart-case`, fzf's default, vim's `smartcase`).
A capital after a backslash is an escape, not text. `*`/`#` keep folding, as
vim's do under `ignorecase`; `:s` shares the `/` compiler and follows it — its
own default is the keys track's decision (0091 §7), not this plan's.

*Alt in a terminal.* Legacy terminals send Alt-x as Escape then x, so the
decoder cannot tell Alt-C from a fast Escape, c. Only the chords the open
picker binds are read as chords, and only while that picker is open; every
other Alt key keeps meaning Escape-then-letter. The cost: Escape followed by
one of five letters within one read (a coalescing SSH link) toggles instead.
Terminals with the kitty keyboard protocol, which strop enables, are exact.

## 4. Content search

### 4.1 Two parallel phases

1. **Gather** the eligible paths with `ignore`'s parallel walker
   (`selection::collect`): same builder, same eligibility function as the
   finder's sorted walk, same 100K-path / 16 MiB bound.
2. **Search** them on `min(cores, 8)` scoped threads, each claiming the next
   eight paths from a shared counter, each with its own `Searcher`. One
   delivery per file (512 rows at most), not one per matching line.

The gathered list is sorted into tree order first — a courtesy, so hits arrive
roughly in the order they are shown and the list grows at the bottom.

A fused walk-and-search (ripgrep's shape) was not chosen: `kind:` queries need
the whole path list before searching, the path bound is simplest to enforce on
a list, and the measured cost of the separate walk is ~70 ms of a 230 ms search.

### 4.2 Order is decided where rows are ranked

Workers finish files in whatever order the disk answers. `rank()` sorts Search
rows by (tree order of path, line, column); `tree_order` compares bytes with
`/` below every other byte, which is exactly the order a name-sorted walk
visits — so lists and goldens are identical to the serial search's. The
serialised search bought that order with a second per query; a sort buys it
for milliseconds, off the input path.

### 4.3 Evidence only when asked for

Project discovery (a second full tree walk) ran on every search to answer
`repo:` atoms. It now runs only for queries that contain one
(`ContentPlan::needs_catalog`), like the symbol index for `kind:`.

### 4.4 Delivery accounting

`BatchProgress::delivery_waiting` becomes a count: several producers wait for
credit independently, and the stall watchdog must not read one of them
resuming as nobody waiting.

## 5. Location rows (B8)

References, implementations and type definitions list as
`path:line  source text`: the path workspace-relative in the file-name idiom
(0088 §2, `render/file_name.rs`), yielding its directory first when narrow;
the source text is what the query filters on. The text for an open document
is its buffer's line. For other local files the language client reads it —
on its own thread, where the reply is decoded, at most 64 files of 1 MiB —
and sends it with the reply (`LspEvent::Locations::sources`). Remote
locations list their place without text.

## 6. `:e` completes what was typed

A plain relative operand (`:e src/ma<Tab>`) completes to `src/main.rs`, not to
a `file:///` URI. Names that are not valid text, or contain whitespace, keep
the lossless URI.

## 7. Budgets

`strop --bench find` and `strop --bench search` time their operations and
**exit non-zero past a budget**; the release procedure (0079) runs them with
the other local qualification steps.

| Scenario | Budget (p95) | Measured here, 32 cores | 4 cores (`taskset`) | 2 cores |
|---|---|---|---|---|
| Finder first paint, 100K paths | 20 ms | 1.4 ms | 3.0 ms | 6.9 ms |
| Finder per-key list, 100K paths | 50 ms | 22 ms | 25 ms | 26 ms |
| Search first hit | 150 ms | 23 ms | 32 ms | 53 ms |
| Search complete | 400 ms | 104 ms | 113 ms | 123 ms |

The per-key budget is for the **list**: the keystroke's ranking installed and
painted. 0091's "key → settled" also waited for the new top row's preview to
be read and highlighted; that is reported beside it, unbudgeted (p95 60–70 ms
when the top row changes file) — it is the preview pipeline's cost, unchanged
by this plan, and it does not hold up the list.

Both scenarios generate their trees: the finder 100,000 empty files, the
search 8,000 source-shaped files (~48 MB) — never a kernel clone. (The
checked-in 97K-path list of §8 is for ranking tests; shipping it in the
binary to bench with would cost half a megabyte.)
0091's 150/400 ms are for the Linux tree on 8 threads; this machine does
150/230 ms there, and 300/440 ms pinned to 4 cores — so on a 4-vCPU CI runner
0091's numbers would not hold on Linux itself. The gate corpus is a twelfth of
that tree, sized so the same budgets hold on 4 cores with room to spare.

Linux tree, warm, before → after (8 threads; `rg -j8` 0.20–0.22 s):

| Query | first hit | complete |
|---|---|---|
| `schedule_timeout_idle` (34 hits) | 837 → 150 ms | 1,152 → 225 ms |
| `kmalloc` (9,068 hits) | — → 90 ms | 1,313 → 255 ms |

## 8. Tests

- **Ranking on a fixed corpus** (`strop-picker/fixtures/linux-7.4-rc2-paths.txt.gz`,
  the 97,362 tracked paths of Linux 7.4-rc2, names only): `sched.h` → the
  twelve files of that name, shortest path first; `sched` → only names
  starting `sched` on the first page; `core.c sched` →
  `kernel/sched/core.c`; `Makefile` → the root Makefile; empty query → the
  priors in order, then the tree. *Deviation:* 0091 expects
  `include/linux/sched.h` first for `sched.h`. Nothing but familiarity
  distinguishes it from `kernel/sched/sched.h`, which is one character
  shorter; it is second, and first once it has been opened — both asserted.
- **Picker state**: 0091's acceptance as written (three batches, a burst-typed
  query, row 0 at every drain, Enter opens the top-ranked path); Enter ahead
  of a ranking; a moved bar follows its item; the empty finder's order;
  frecency on a typed query; `Space b` resting row; `Ctrl-U`; each toggle's
  effect on results and on the status row; smart case.
- **Search**: hits from 160 files across directories whose byte order differs
  from tree order rank in tree order; cancellation stops the searcher within
  its delivery credit.
- **Goldens**: location rows; a toggled search with its status row; the
  existing files and grep scenes.
