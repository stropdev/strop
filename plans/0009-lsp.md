# 0009 — LSP

> How strop talks to language servers: Helix's registry model, async-lsp's
> transport, our async invariant. The zero-config promise decides the
> shape as much as the grammar does.

Status: accepted-in-principle. Implementation begins with diagnostics
(0001 roadmap: diagnostics-only slice may pull forward).

---

## 1. Research (2026-09-02)

| Editor | Registry | Install | Transport |
|---|---|---|---|
| Helix | `languages.toml`, ~281 servers (command+args) | never — PATH only | hand-rolled JSON-RPC (helix-lsp, tokio) |
| Zed | built-in registry + download-on-demand (npm/pip) | auto-downloads | own |
| Neovim | nvim-lspconfig (community, no install) + mason (installer) | separate tool | vim.lsp (lua) |

The split that matters: **registry and installer are different concerns**.
nvim-lspconfig vs mason prove it. We take Helix's half: a curated
registry, no installer — zero-config means "works with what you have",
not "we silently npm-install into your life".

## 2. Decisions

1. **`async-lsp` (tower-based) is the transport.** Hand-rolled JSON-RPC is
   vanity (the critique was right); async-lsp gives router/lifecycle/stdio
   and is used in production by other editors. `lsp-types` re-exported.
2. **Tokio lives in a worker thread**, never the input path. The editor's
   event loop drains a channel; the LSP runtime posts onto it — the same
   pattern as picker workers and git jobs (0001 §5.6 holds).
3. **Embedded registry** in `strop-lsp` for our curated languages:
   rust-analyzer, clangd, pyright (or basedpyright), gopls,
   typescript-language-server, bash-language-server, vscode-json-languageserver.
   Config overrides or adds servers — helix-style `languages.toml`,
   layered project > XDG > embedded (0012) — data, not code.
4. **No auto-download.** Missing server = one statusline hint with the
   install command (`brew install rust-analyzer`, `npm i -g …`), once per
   session. Never a network fetch from the editor binary.
5. **Server capability gating** from day one (helix-lsp's
   `supports_feature` pattern) — servers lie about what they do.
6. **Encoding boundary**: UTF-8 internally (0001 §5.1), UTF-16 at the LSP
   boundary, conversion centralized in `strop-lsp` — and assume servers
   lie about their encoding.

## 3. Landing order

- **Wave 1 — diagnostics.** Server spawn (per workspace root), didOpen /
  didChange (debounced) / didClose, publishDiagnostics → gutter signs
  merged with git signs (the M2 column-merge logic), `Space d` picker
  over them. This is the whole "is LSP alive" proof.
- **Wave 2 — navigation & info.** `gd` goto-definition, `Space k` hover
  card, `Space s`/`Space S` symbols (LSP-backed when a server is up,
  tree-sitter outline otherwise).
- **Wave 3 — editing.** `Space r` rename (semantic; complements the
  textual 0007 replace), `Space a` code actions, completion in insert
  (`ctrl-n`/`ctrl-p` native first; async popup second), `gq` format.

## 4. Crate shape

```
strop-lsp     registry, client wrapper, diagnostics store, encoding
              boundary, capability gating. Owns the tokio runtime thread.
```

The editor crate consumes `strop-lsp` through a channel of typed events
(`Diagnostics { path, items }`, `HoverReady { … }`, …) and never sees an
async type. If this module outgrows ~800 lines, split by concern
(client.rs / registry.rs / diagnostics.rs / requests.rs) — the AGENTS
rule applies.

## 5. Explicitly out

- Auto-downloading servers (see §2.4).
- Workspace folder UI (root = the git/file root of the first buffer; multi-root later).
- DAP (debugging) — a different project.
- Server-specific configuration beyond `initialization_options` passthrough from config.
