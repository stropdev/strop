# Strop RFCs

Use [GitHub issues](https://github.com/stropdev/strop/issues) for work and [milestones](https://github.com/stropdev/strop/milestones) for release scope. Start with the [next development cut](https://github.com/stropdev/strop/milestone/81) for pickup order or [Later](https://github.com/stropdev/strop/milestone/1) for unscheduled work. An RFC records the decision, why it was made and what actually landed. The [changelog](../../CHANGELOG.md) and [published releases](https://github.com/stropdev/strop/releases) are the shipping record.

## When and how to propose a decision

1. Search the registry and open or find the issue. A fix that restores existing behaviour needs an issue and a regression witness, not another design. An RFC is for costly decisions: key grammar or interaction contracts, preview/execute semantics, persisted formats, new host authority/dependencies, kernel boundaries or release policy.
2. Follow [governance](../../GOVERNANCE.md). Copy [0000-template.md](0000-template.md) to `YYYY-MM-DD-kebab-title.md` using its drafting date. Keep the filename on retitle. Link the issue from the RFC and the RFC from the issue, apply `rfc` in place of `needs-rfc`, and add a registry row (new entries have no legacy ID).
3. For a kernel change, state the theorem over the shipped Rust and the mutant that must break it **before** the design. Name the host assumptions, Neovim comparisons and real-buffer/terminal checks outside the proof. No RFC waives [Strop’s engineering rules](../../AGENTS.md).
4. Only the maintainer accepts or rejects a design. A draft can be merged for discussion. Record the decision and rationale; a milestone assignment or a merged draft is not approval to implement. On replacement, link old and new records both ways. Amending a section does not supersede an entire RFC.
5. Reference the issue in implementation PRs. Update `implementation` and the as-built note with the actual outcome. Use `Closes #N` only when the agreed work lands, and split remaining work into issues rather than keeping another roadmap here. See [Contributing](../../CONTRIBUTING.md).

| Frontmatter | Meaning |
|---|---|
| `rfc`, `title`, `authors`, `created`, `updated` | Stable filename stem, decision title, contributors, drafting and last material revision dates. |
| `status` | `draft`, `accepted`, `rejected`, `superseded` — a decision, not a ship claim. |
| `implementation` | `not-started`, `in-progress`, `partial`, `complete`, `removed`, `n/a`. Complete applies to the **agreed slice**, not to future ideas in its text. |
| `issue`, `milestone` | Canonical issue URL and assigned milestone at last update (or `null`); GitHub owns live state and scheduling. |
| `supersedes`, `superseded_by`, `blocked_on` | RFC IDs in both directions for whole-record replacements; concrete dependencies or owner questions. |
| `legacy_id` | Backfill only. Never allocate a new serial number. |

## Reading the backfill

This follows [Gripsack’s import](https://github.com/gripsack-dev/gripsack/blob/main/docs/rfcs/README.md), [Writfold’s RFC lifecycle](https://github.com/writfold-dev/writfold/blob/main/docs/rfcs/README.md) and [Omnigraph’s issue-first governance](https://github.com/ModernRelay/omnigraph/blob/main/GOVERNANCE.md). The [last tracked tree](https://github.com/stropdev/strop/tree/eec2a0e7fe62bb75461d6d779c9dea514a80a4f9/plans) and [final status ledger](https://github.com/stropdev/strop/blob/eec2a0e7fe62bb75461d6d779c9dea514a80a4f9/plans/STATUS.md) are immutable sources, not active checklists. The registry replaces the ledger; issues replace the roadmap (0028).

Every original design has a disposition, issue and full design text. **Read the as-built paragraph first**: old status lines, checkboxes, commands and proposed schedules below it describe their time. Source links in historical designs point to contemporary code, including removed components. The Git addition’s author/date identify the first recorded copy, not necessarily its sole author or decision date. GitHub import dates are not historical ship dates. A closed retrospective issue can describe removed or partial work; its linked open issues own the remainder.

Old citations such as `plan 0104 §4` or `plans/0104` in code, fixtures and past releases are legacy IDs below, not lookups in a live directory. **0052 never existed. Both 0083s shipped** (Splicery and Weft; distinct records). **0084** was an untracked working-tree proposal missing from the ledger; the import preserves it without attributing authorship or claiming it shipped. **0058’s native worker was removed by 0090**; the older ledger only recorded the retirement of its proof machinery. The DAP sketch 0019 was replaced by another proposal, not an accepted debugger.
